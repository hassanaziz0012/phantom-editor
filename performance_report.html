Architectural & Pipeline Evolution

Before today's refactoring, the pipeline operated as a series of isolated script invocations, forcing the input video to be fully decoded, filtered, and re-encoded up to 3 separate times on disk. Intermediate files were written sequentially, and heavy audio noise reduction was executed on silent un-trimmed portions.

❌ BEFORE: Legacy Multi-Pass Execution

  • Pass 1 (Webcam Masking): Encoded video with preset medium, crf 18 & written to intermediate temp video file.
  • Pass 2 (Silence Trimming): Re-decoded intermediate video, applied Silero VAD, and re-encoded video again to a 2nd temp file.
  • Audio Denoising Bottleneck: Ran DeepFilterNet sequentially on 100% of untrimmed raw audio on a single CPU core.
  • Normalization Overhead: Executed extra FFmpeg pass solely for audio normalization writing normalized.wav.
  • Sequential Transcription: Dispatched large single audio file to Groq API with 48kHz stereo payload size.

✅ AFTER: Streamlined Single-Pass Architecture

  • Single-Pass Video Processing: Webcam masking & silence trimming filter expressions combined into ONE FFmpeg graph execution pass.
  • Pipeline Step Reordering: Silence trimming occurs BEFORE audio noise reduction—reducing audio duration by 30%-50% prior to denoising.
  • Parallel Denoising: Audio split into 60s chunks & processed across all CPU cores simultaneously via GNU Parallel/Sox.
  • Merged Audio Remuxing: Integrated loudnorm filter directly into the remux command with dual stream output.
  • Parallel Transcription Chunking: Audio downsampled to 16kHz mono, split into 10m chunks & sent via ThreadPoolExecutor.

The Issue / Bottleneck

Transcribing long video audio files via Groq API in a single HTTP payload suffered high latency, file payload size constraints, and potential request timeouts without concurrency.

How it was Fixed

Implemented chunked transcription. Audio files longer than 10 minutes are split into chunks using FFmpeg and dispatched concurrently via ThreadPoolExecutor(max_workers=4) with Groq RPM rate limiting and exponential backoff retry logic.

BEFORE (Sequential Single Request)

with open(audio_path, "rb") as file:
    transcription = client.audio.transcriptions.create(
        file=(audio_path.name, file.read()),
        model="whisper-large-v3",
        response_format="verbose_json"
    )
AFTER (Concurrent Chunked API Requests)
# Split audio into ~10-minute chunks
chunks = split_audio_into_chunks(audio_path, chunk_duration_sec=600)

# Dispatch chunks in parallel with ThreadPoolExecutor
with ThreadPoolExecutor(max_workers=4) as executor:
    futures = [executor.submit(transcribe_chunk, chunk, idx) for idx, chunk in enumerate(chunks)]
    results = [f.result() for f in futures]

srt_content = merge_transcriptions(results)

Commit 9 345ca30 parallelize DeepFilterNet audio processing across CPU cores
Audio
Files Modified
audio-processing/noise_reduction.sh
The Issue / Bottleneck

The deep-filter CLI tool operates single-threaded by default. On multi-core CPUs, processing full-length audio files left 90%+ CPU capacity idle while running extremely slowly.

How it was Fixed

Used sox to split audio into 60s chunks, dispatched deep-filter invocations in parallel across all available CPU cores (nproc), and concatenated output chunks with FFmpeg.

BEFORE (Single-Threaded Execution)
# Executed deep-filter on single CPU core
deep-filter -o "$TMP_DIR" "$INPUT_FILE"
AFTER (Multi-Core Parallel Chunk Denoising)
# Split WAV into 60s chunks with Sox
sox "$INPUT_FILE" "$IN_CHUNK_DIR/chunk_.wav" trim 0 60 : newfile : restart

# Run deep-filter in parallel across all CPU cores
find "$IN_CHUNK_DIR" -name "chunk_*.wav" | parallel -j "$NUM_CORES" deep-filter -o "$OUT_CHUNK_DIR" {}

# Concatenate filtered chunks seamlessly with FFmpeg
ffmpeg -f concat -safe 0 -i "$CONCAT_LIST" -c copy "$GENERATED_FILE"

Commit 5 3c87d61 Incorporate loudnorm filter into remux step in process_audio

Files Modified

The Issue / Bottleneck

The audio pipeline ran normalize_audio.sh as a standalone FFmpeg pass, writing an intermediate normalized.wav file to disk prior to remuxing into the final MP4.

How it was Fixed

Integrated EBU R128 audio normalization (loudnorm=I=-16:TP=-1.5:LRA=11) directly into the final FFmpeg remuxing command using dual stream mapping, eliminating intermediate WAV file creation.

BEFORE (Separate Normalization Step & Disk File)
# Step 4: Standalone audio normalization pass
"$SCRIPT_DIR/normalize_audio.sh" "$NOISE_REDUCED_WAV" --output-file "$NORMALIZED_WAV"

# Step 5: Replace audio in original MP4
ffmpeg -y -i "$INPUT_MP4" -i "$NORMALIZED_WAV" -c:v copy -map 0:v:0 -map 1:a:0 -c:a aac "$OUTPUT_MP4"
AFTER (Single Remuxing Pass with Integrated Normalization)
# Single FFmpeg pass applying loudnorm while remuxing video and writing audio
ffmpeg -y -i "$INPUT_MP4" -i "$NOISE_REDUCED_WAV" \
    -c:v copy -map 0:v:0 -map 1:a:0 \
    -af "loudnorm=I=-16:TP=-1.5:LRA=11" -c:a aac -b:a 384k "$FINAL_MP4" \
    -map 1:a:0 -af "loudnorm=I=-16:TP=-1.5:LRA=11" -c:a pcm_s24le -ar 48000 "$PROCESSED_WAV"
